# 开发日志:eCallisto 爬取 + RFI 除噪(SumThreshold)

阶段性总结,覆盖本轮新增的两个模块:`ecallisto_grabber/`(爬取)和 `ecallisto_grabber/denoising/`(除噪)。这两个模块是独立于 `radburst_tl/` 原有 pipeline 之外的新分支,不修改、不依赖原 pipeline 的任何代码。

## 目标

原计划:先在 eCallisto 全网数据上做 transfer learning 预训练,再迁移到自己站点的小数据集上做射电暴分类。这需要两件事:(1)能自动爬取 eCallisto 原始数据 + burst 标注,不依赖人工 GUI 标注;(2)一个比现有 `denoise_new.py` 更可靠的 RFI 清洗算法,同时能处理 eCallisto 和自己站点两种数据源。

## 模块一:`ecallisto_grabber/`(爬取)

以队友 Callen Fields 的脚本(`Prepro-F25/one_day.py`)为蓝本重写,扩展为同时抓取原始频谱数据和 burst 时间/类型标注(来自 soleil.i4ds.ch 的 Monstein 目录,人工核验、2010年至今持续更新)。

### 文件结构
- `burst_catalog.py` — 拉取/解析 Monstein 月度目录文本文件,`filter_catalog()` 按站点/类型/是否确认过滤
- `fetch.py` — 下载指定站点某天的 FITS 文件并拼接成完整频谱图,处理频率轴标定、采样间隔
- `extract_events.py` — 按目录里的 burst 时间窗口切出事件片段,`sample_negative_windows()` 采负样本
- `scrape.py` — 主入口,支持 `--count-only` 先估算规模不实际下载
- `rfi_quality.py` / `survey_stations.py` — 抽样评估站点 RFI 严重程度,用于站点筛选
- `preview.py` — 生成频谱图预览图,人工目视质检

### 已验证的关键 bug 修复
- `TIME-END='24:00:00'` 这种午夜时刻的解析(datetime 不接受小时=24,用 divmod 处理跨天)
- 跨文件间隙感知的时间索引(真实站点数据有设备/网络中断造成的空档,原本会导致后续事件被静默错位或丢失)
- 同一分钟内多个事件的文件名冲突(文件名加入结束时间+类型)
- 同一天内偶发切换采样配置(如 Australia-ASSA 混用 200/400 通道),原本"取第一个文件的配置、丢弃不匹配的"会丢掉大部分数据,改为"保留当天多数文件所用的配置"
- **同一时刻多接收机重复文件**(`fetch_station_day`)——部分站点(已确认 ALASKA-HAARP、AUSTRIA-UNIGRAZ)每个时间戳会发布两份独立文件(URL 后缀 `_62`/`_63`),通道数、频率范围完全相同,但数据本身不同(逐行相关性约 0.06,不是重复副本,是两台独立接收机)。原逻辑只按通道数分组、不检测时间重叠,会把两组并行数据当成顺序数据首尾拼接,导致当天频谱图时间轴翻倍、后续所有基于列号的时间索引(包括每一个 cataloged event 的裁剪位置)全部错位。ALASKA-HAARP 2024-03-07 实测 44 个文件里有 21 个是重复接收机;AUSTRIA-UNIGRAZ 2024-03-01 45 个文件全部成对。已修复:按 (time_obs, url) 排序后,检测时间重叠 >50% 的相邻文件,确定性地只保留一份。修复前后总列数对比验证过(修复后精确匹配"文件时长总和/采样间隔"的理论值)。

### 现状:未完成的部分
- **从未跑过真实规模的抓取**。此前估算过候选站点范围(按频段接近自己站点、RFI 质量抽样筛选后约 10 个站点、495 station-day、预计 7 小时),但一直没有实际执行全量抓取,只用于测算规模。
- RFI 质量抽样筛选(`rfi_quality.py` 排出的站点排名)后来发现存在盲区——早期版本对"大范围、中等强度、分散式" RFI 不敏感,排名可能不完全可靠,如果要用它来做正式站点筛选,建议先用当前除噪算法里验证过的方法重新抽样看几个站点。
- 退化/标定通道(某些 FITS 文件末尾 7-8 行是 duplicate frequency 的锯齿标定信号,不是真实频谱)只在测试脚本里临时用 `valid_rows = np.concatenate(([True], np.diff(freq_mhz) != 0))` 处理过,还没整合进 `ecallisto_grabber` 正式模块。
- 多接收机重复文件目前只在 ALASKA-HAARP、AUSTRIA-UNIGRAZ 两个站点上实测确认过,没有扫描全网站点统计还有哪些站点受影响——正式全量抓取前建议先跑一次 `--count-only` 附带的去重日志,摸底受影响站点范围。

## 模块二:`ecallisto_grabber/denoising/sumthreshold_denoise.py`(除噪)

### 为什么不用现有的 `denoise_new.py`

`denoise_new.py` 的核心问题:Step 1 对每个频率通道做归一化(减去自己的中位数、除以自己的 MAD),Step 3 检测持续性 RFI 时又是拿归一化后的通道去跟自己比——如果一个通道从头到尾都被 RFI 均匀污染,归一化会把这个污染"吸收"成该通道自己的正常水平,之后再也检测不出来。这个"跟自己比、比不出整体偏移"的陷阱在本轮除噪开发里反复出现(竖直方向、行方向各遇到一次),是选择重新设计算法而不是修补原算法的主要原因。

### 算法选型过程

评估过三条路:(1) 修复现有 AGBS→AMF→FPBS 流程的边缘 bug;(2) 从零实现 SumThreshold(RFI 检测的业内标准算法,Offringa et al.);(3) 其他方案(小波+形态学、NL-means等,评估后判定难度/收益不如前两者)。

先按优先级尝试了方案(1),用肉眼比对发现"protect 区域是硬边界"和"rolling mean 被附近 burst 污染"两个根因,修复后仍有残留的蓝色"护城河"伪影,几轮独立的变量隔离实验都无法完全消除,判断是 AGBS"逐行独立处理"这个方法本身的结构性限制。转向方案(2),最终定型。

### 核心架构(`clean()` 函数,自顶向下)

1. `robust_smooth_background` — 2D 平滑背景拟合,迭代排除离群值(burst 和 RFI 都是"不平滑"的,都要排除),离群值判断按**每一行自己的**中位数/MAD(不是全图统一一个阈值——全图统一阈值下,一个真实 burst 往往不够极端,只有峰值像素会被排除,导致背景拟合被 burst 污染)
2. `persistent_row_correction` — 跨行(跨频率通道)比较持续性偏移,修复上面提到的"归一化吸收整体偏移"问题
3. `per_row_normalize` — 每行按自己的 MAD 归一化,让后续统一的 sigma 阈值在不同频率通道间可比
4. `vertical_rfi_weight` — 判断某一时刻是否为瞬时宽带 RFI,依据是**跨频率覆盖率**(有多少比例的通道同时异常)而不是幅度——真实太阳暴哪怕宽带,也很少能同时打满所有频率通道(传播/频散效应),但地面瞬时干扰(如电气开关噪声)可以。这个判据是从 `denoise_new.py` 已经验证过的 Step 2 逻辑移植过来的,只是换成了跨行归一化后的连续版本
5. `burst_weight_2d` — 2D 连续 burst 权重(在频率和时间两个方向都做平滑),取代早期"按列判断、频率方向不敏感"的版本——旧版本对漂移暴(Type III 频率随时间扫过)只能整列保护或整列不保护,做不到"这一列只有中间几行是 burst"
6. SumThreshold 多尺度扫描(`sumthreshold_axis_ratio`,时间轴+频率轴各一次)— 输出连续 ratio 而非二元 flag
7. 连续抑制:`frac = clip(ratio/suppression_ramp, 0, 1)`,再用 `vertical_rfi_weight` 作为抑制下限(`frac = max(frac, vrfi_weight)`,但排除受保护区域)——单纯按 ratio 抑制对极端 RFI(残差幅度可达正常信号的百倍量级)不够彻底,即使抑制了 80% 以上,剩下的绝对值仍然远超正常信号

全程没有任何硬 0/1 切换——从背景拟合的离群值判断,到 burst 保护边界,到最终抑制强度,都是连续过渡,这是本轮调试反复验证过的经验:任何硬切换都会在边界处留下视觉可辨的伪影(白块/色斑/飘带)。

### 关键设计:ground truth 优先于自动检测

`known_burst_weight` 参数——如果调用方能提供真实 burst 时间(own-station 有 catalog,eCallisto 有 Monstein 目录),直接强制保护对应区域,不管自动检测怎么判断。这不是可选优化,是必需项:今天验证发现,纯自动检测(`burst_weight_2d`)在不同站点上的可靠度差异很大(盲测保留比例 20%~74% 不等),不能单独依赖。

### `sumthreshold_cleaning_wrapper()` —— 对接现有 pipeline 的接口

跟 `denoise_new.advanced_rfi_cleaning_wrapper()` 完全同签名(`spectral_data, burst_start_idx, burst_end_idx, burst_type, method`),可以直接替换 `radburst_tl/data_preprocessing_new/slicing_utils_new.py` 里的 import,不需要改调用方代码。**目前尚未实际切换这个 import**——新模块已就绪、已验证,但默认流程仍在用旧的 `denoise_new.py`,切换与否由用户决定。

内部做了两件事调用方不用关心:
- `time_win` 按 `sample_interval_s` 自动换算(自己站点 0.1s、eCallisto 常见 0.25s,同样的采样点数对应的物理时长不一样,已修过一次因此导致 burst 保护窗口过窄的 bug)
- 数据全程 float32(不是 numpy 默认的 float64)——大文件内存吃紧时的关键优化,详见"已知限制"

### `clean_ecallisto_events.py` —— eCallisto 侧的对接(catalog 时间 -> known_burst_weight)

`sumthreshold_cleaning_wrapper()` 是为 own-station 的 CSV/DataFrame、`(time, frequency)` 输入设计的;`extract_events.py` 存的 `.npy` 已经是 `(frequency, time)`(`clean()` 原生方向),不需要也不应该走同一个 wrapper。这个新文件是 eCallisto 专用的对接层:

- `event_burst_indices(row, sample_interval_s)` —— metadata.csv 里存的是**含 buffer 的窗口**(`start_time`/`end_time`)和**真实 catalog 事件时间**(`event_start_time`/`event_end_time`)两套时间戳,event 在裁剪出来的 `.npy` 里的列位置 = 两者之差 / 采样间隔,不是从 0 开始。
- `clean_event_file(npy_path, row, ...)` —— 读一个事件的 `.npy` + 对应 metadata 行,算出 `known_burst_weight`,调用 `clean()`。负样本(`type=="0"`,`event_start_time` 为空)自动跳过保护,直接走纯 RFI 清洗。
- `clean_all_events(out_dir, ...)` —— 批量处理某次 `scrape.py` 输出目录下 `metadata.csv` 里的所有行。

## 已验证效果(本轮测试record)

- **own-station**:6 个真实标注文件(Type II×2、Type III×3、Type V 未单独测但逻辑相同,跨 SkylineHighSchool / PeachMountian / Huron / MarquetteSeniorHig 四个站点),burst 保留稳定,持续性横线 RFI 大幅减轻,瞬时宽带竖线 RFI 基本消除(有 known_burst_weight 兜底的前提下)
- **eCallisto,真实爬虫输出**:实际跑了两次小规模真实抓取(AUSTRIA-UNIGRAZ 3 个 Type III、ALASKA-HAARP 1 个 Type II,共 4 个真实 positive 事件,均在发现并修复 `fetch.py` 去重 bug 之后重新抓取确认),`clean_ecallisto_events.py` 处理后,4 个事件的保护区域抑制强度全部精确为 `0.000000`,`|raw残差|` 与 `|cleaned|` 逐像素相等——ground truth 保护机制在真实爬虫输出上验证通过,不再依赖此前手动缓存的测试 crop。

## 已知限制 / 待办事项

1. **内存**:处理时长较长(几十万行)的真实文件时峰值内存可达 12-13GB(15GB 内存的机器上余量偏紧)。已用 float32 大幅优化过(此前是 float64,内存减半),但如果要批量处理全部 101 个 own-station 文件,建议先摸底最大文件的内存需求,或考虑处理前按需裁剪掉事件时间窗口外的大段无关数据。
2. **持续性横线 RFI 是"减轻"不是"消除"**——`persistent_row_correction` 只修正了每行的整体偏移(常数项),没有处理该行自身的纹理/波动,清洗后仍有可辨的细横纹残留。
3. **一个未完全定性的边缘案例**——随机抽样验证时,一个 Type II 样本(`240514120913-Skyline High School.csv`)在标注 burst 窗口之外出现了一条疑似过度抑制的蓝色条带,burst 本身没有被破坏,但没有深入排查这条带的成因。
4. **RFI 质量站点筛选**(`rfi_quality.py`)的排名可靠性存疑,见模块一部分。
5. **多接收机去重的站点覆盖面未知**,见模块一"现状"部分。
6. eCallisto 目前只用 2 个站点、4 个真实事件验证过对接机制——机制本身(catalog 时间 -> known_burst_weight)是通用的,但还没有像 own-station 那样跑过跨站点、跨类型的随机抽样批量验证。

## 模块三:`extract_windows.py` —— 15 分钟窗口抽取(2026-08-11 新增)

架构在 `TRAINING_PLAN.md` 里改成"COCO预训练 YOLO + 目标检测"之后,原来的 `extract_events.py` 输出不能
直接用了。这里记的是**为什么要写第二条抽取路径**,以及这一轮踩到的坑。

### 触发原因:`extract_events.py` 的输出有标签泄漏,而且不报错

`extract_events.py` 裁的是"事件 ± `buffer_s`(60s)",所以**事件必然在 crop 正中央**。在真实输出上实测:

```
normalized box CENTER within crop:  mean 0.5000   std 0.0000   min 0.500   max 0.500   (n=1694)
```

对分类任务无害(框坐标不进模型),对检测任务是致命的:模型恒定在水平正中央画框就能拿到很高的定位分,
Phase 1 想要的那个"证明或证伪 pipeline"的 mAP 数字**变得无法解读**。

**教训**:做检测/定位任务之前,先统计一遍标签在图里的位置分布——一行代码的检查,漏掉就是整轮实验作废。
任何"以目标为中心裁剪"的数据集构造方式都有这个风险,包括以后给 own-station 设计窗口构造的时候。

### 顺带发现:`cleaned_events/` 对被人工修正过的事件是坏的

生产清洗用 **catalog 时间**建 `known_burst_weight`,而 `event_review` 的人工修正恰恰说明 catalog 时间
是错的(80% 往后挪、66% 挪动 >10s)。结果是保护窗口保护了空白处,真实 burst 在没有 ground truth 保护
的情况下被去噪。132 个有修正的事件里 **42% 的修正框完全落在保护区间之外**(纯算术统计),肉眼比对
raw/cleaned 确认 burst 确实被抹掉了。

**这不是代码 bug** —— `clean()` 忠实保护了传给它的区间,是喂进去的值本身错了,跟 own-station 那次
"时间算出来了但从没传进 `clean()`" 是不同性质的问题(那次是代码 bug,这次是数据过期)。真正暴露的是
`burst_weight_2d` 自动检测兜底不够强:保护窗口之外它没能自己认出 burst,这是本文档早就记过的已知限制。

**推论**:审核时看到的"burst 偏淡/被抹除",有一部分是这个原因造成的假象。给 `burst_faint` 标签调参数
之前,先确认时间段对不对。

### 顺带发现:原始 FITS 从来没有缓存过

`extract_events.py` 是边下边裁只存 crop,所以任何"想换个切法"的需求都要重新下载。已决定
`extract_windows.py` 缓存"事件所在 15 分钟槽 ± 2 槽"(±30 分钟上下文),覆盖到 75 分钟画布,全 7 站
19.8 GB。**`fetch_station_day()` 反正是整天下载,缓存粒度只影响磁盘、不影响耗时。**

估算存储时还踩过一次:最初按 24 小时观测估 Arecibo 全天缓存 29 GB,实测 scrape 日志里中位数只有
**49 个文件/天**(约 12 小时——站点只在本地白天观测),真实 15.2 GB。**估容量前先看日志里的真实
files/day,别按 24 小时算。**

### 设计要点

- 单元 = 归档自己的 15 分钟 FITS 文件(不自己切边界),uint8 `.npy`,一槽一文件
- 框的时间源优先级:`event_review` 人工修正 > catalog 时间;零宽度 catalog(占正样本 36%)套
  `catalog_start + 10s`、宽 `35s` 的默认值(依据见 `TRAINING_PLAN.md` "Bounding box 构造")
- 负样本 = 窗口内没有任何目录事件,不再需要 `sample_negative_windows()` 那套逻辑
- **判定"干净负样本"必须用全类型目录**(`explode_by_station` 未过滤版),不能只看 II/III/V——
  含 Type IV/I 的窗口既不能给框也不能算负样本,要整窗排除。这条沿用 `extract_events.py` 里
  `_free_intervals()` 已经做对的判断

### 试点验证:11 个 Arecibo station-day(2022-01),三个 bug 全是真实数据跑出来的

跑了 2022 年 1 月全部 11 个 Arecibo station-day:**137 个窗口、95 MB、平均 64s/station-day**,
跟"全站 432 天 / 9 小时 / 6.6 GB"的预估一致。三个 bug 全部是"代码逻辑上没问题、撞上目录脏数据"的类型,
**读代码看不出来,只有跑真实数据 + 出图才暴露**:

1. **越界排除规则被长条目放大成全天灾难**。原规则"窗口里有任何非 II/III/V 事件就排除",遇上
   `CTM 00:00-23:59`(连续辐射风暴,中位时长 112 分钟,本来就该持续数小时)直接团灭整天:20220130
   23 个窗口排除 23 个,而那天有 11 个 Type III。全数据集口径:47/435 个 station-day 带 >60min 的
   CTM/VI 条目,挂着 **12% 的正样本**。
   **修法**:只有"本来会当负样本"的窗口才因越界事件排除。理由是两种标注说的话不一样——负样本说的是
   "这整段时间没有 burst",有个 Type VI 在里面这句话就是假的;正样本说的是"这里有个 Type III,在这个
   位置",背景有连续辐射风暴不影响它为真。越界类型记进 `offclass_types` 列,信息不丢。
   修复后 20220130 排除 15/23、20220131 排除 14/34(原 30/34)。
2. **目录笔误撞上正确的跨午夜处理**。`_parse_time_range` 遇到"结束早于开始"会 +1 天,这对真实跨午夜
   事件是对的,但目录里的 `18:27-18:26`(20221111)和 `19:00-10:02`(20230306)是笔误,被解释成 1439 分钟
   和 902 分钟,会在那一整天的每个窗口上刷一条满宽满高的框。
   **修法**:`MAX_EVENT_DURATION_S = 60min` 上限,超过打印警告后跳过。阈值不是拍的:1759 个目标事件里
   最长的合理事件是 34 分钟的 Type II,>60 分钟的恰好只有这 2 个笔误,阈值正好落在空隙里。
3. **跨窗口边界的碎片框**(出图查框宽分布才发现)。一个 19:15-19:19 的事件骑在窗口边界上,
   `19:00:01-19:15:01` 只分到 **4 列 = 1.0 秒**,剩下 956 列在下一个窗口。一个满频率高度、宽 1 秒的框
   里没有任何可辨认的 burst 结构,**长得跟一条 RFI 竖线一模一样**,等于教模型把 RFI 当 Type III。
   **修法**:`MIN_BOX_S = 5.0` 下限(试点里人工标注的最窄真实 burst 是 10 秒、25% 分位 20 秒,5 秒两边
   都有余量)。唯一的框被丢掉的窗口标 `only_edge_sliver_of_an_event` 排除,**不能降级成干净负样本**——
   里面确实有 burst,只是不够完整。

### 试点确认的效果

**标签泄漏消失**(这是整轮改造的核心目的):

```
框心归一化位置:  mean 0.4680   std 0.2912   min 0.011   max 0.966
落在 0.49-0.51:  6%              <- 每事件 crop 时代是 100%,std = 0.0000
```

肉眼看图:绿框(人工修正)最可靠,基本压在可见 burst 上;红框(catalog 原始)偏宽,有一例框住左边的
burst 却漏掉右边的另一个;橙框(零宽度默认值)经常落在看不出东西的地方——**跟当初 58% 的留出集
IoU≥0.5 命中率吻合,没有意外**。

### 新发现的、没解决的问题:目录漏收 burst

出图能看到**目录没收录但肉眼明显的 burst**(如 20220131 14:15 那个窗口,框外 3.2-3.6 分钟处有一个)。
活跃日的 Monstein 目录不会逐条收录每一个 Type III(这也正是 Type VI "一串 Type III" 这个类别存在的
原因)。这不是我们的 bug,是目录本身的性质,但会让检测器"正确检出未标注 burst"被算成误报,**压低
Phase 1 的 precision 读数**。解读 mAP 时必须记得这一层,不能把低 precision 直接当成模型不行。

## 模块四:Type II/V 改用「最小处理」视图(2026-08-12)

### 起因:审核时发现参数滑块对长 Type II 完全没反应

用户报告调滑块看不出变化。实测七个参数,**保护区内每一个的影响都精确为 `0.0000`**(全图 max|diff| 最高
到 50,但全在保护区外)。原因是 `known_burst_weight` 的设计:保护区内抑制强度强制为 0,所有下游参数
在数学上失效。而那条 Type II 的 catalog 窗口是 60-1080s,**保护区占整幅图 90%** —— 所以肉眼几乎看不到
任何变化。这不是 bug,是设计,但对用户完全不直观。

### 更严重的:burst 在背景拟合阶段就没了,比任何滑块都早

同一条 Type II 的实测:

| | 数值 |
|---|---|
| raw 里 burst 的真实超出量 | 23.30 |
| 背景模型从 136.67 抬到 159.36 | **吸收了 97%** |
| cleaned 里剩下 | 0.52(**2%**) |

而且 `residual == cleaned` 完全一致(保护区抑制为 0),证明损失确实发生在背景拟合。

**根因**:`clean()` 第 315 行调用 `robust_smooth_background(data, freq_win, time_win, bg_iter, bg_sigma)`,
**签名里根本没有 `known_burst_weight`**;它到第 336 行才被用于合并 `burst_weight`。也就是说
**ground truth 时间传进了 `clean()`,但 `clean()` 内部没往下传给背景拟合**。

背景拟合本来靠"迭代排除离群值"避开 burst,前提是 **burst 是离群值**。一个持续 800 秒、占据整行 70% 的
Type II 不是离群值,它就是那一行的主体 —— 排除机制在最需要它的时候失效。这与 `per_row_normalize` 的
docstring 里"a real burst is a small minority of the timeline"是同一个假设,长事件上同样不成立。

### 试过的"根治方案"是错的,已证伪,不要再走这条路

朴素改法(把 `known_burst_weight` 传进 `robust_smooth_background`,强制保护列不参与拟合)实测:

| | 保护区内背景 | 保护区外背景 | 保护区内 cleaned |
|---|---|---|---|
| 当前代码 | 151.08 | 136.11 | 0.22 |
| **朴素改法** | **0.00** | **6.82** | **150.99**(raw 是 151.68) |

背景吸收确实降到 0%,但**背景估计整个塌成 0**:`known_burst_weight` 是全频率广播的,等于把 90% 的列
所有频率行都排除出拟合,`uniform_filter` 窗口(241 采样 = 60 秒)落在保护区中心时窗口内几乎没有有效
像素,`den→0`、`num→0`,背景归零,连保护区外都被带坏。结果 `cleaned ≈ raw`,等于完全不做背景扣除。

**要做对,背景在保护区内必须靠周围未保护数据插值**,而这里是"用两侧各约 60 秒去外推 1025 秒",没有
明显正确答案。**这不是四行能解决的事。**

### 采用的方案:Type II/V 默认走 `minimal_view()`

`data_access.minimal_view()` = 只做逐行中位数扣除,**零抑制**,所以不可能抹掉 burst。它去掉的是压住
`render_pair` raw 面板的通道直流偏移(那个面板画的是完全未归一化的原始值)。

**决策依据是肉眼比对 8 条已审为 usable 的 II/V**(raw vs 当前 cleaned):

| 结果 | 条数 |
|---|---|
| cleaned 几乎抹掉微弱 burst | 2/8(都是 prot=4% 的短 V,catalog 零宽度使保护形同虚设) |
| cleaned 引入硬边界断裂 | 1/8 |
| **cleaned 明显更清晰** | **1/8** |
| 基本持平 | 4/8 |

所以"II/V 不需要去噪"**大体成立但不绝对**——1/8 的情况去噪确实更好。因此实现成**默认值而不是删除**:
面板上有「改用完整去噪版」勾选框,那 1/8 可以随时切回去。

验证:Type II 的基频+谐波带在最小处理版上完整可见(当前 cleaned 几乎全空);微弱 V 的通道条带去掉后
burst 也露出来了。

**注意色标**:最小处理版的量级是 raw 自身量级(几十),比被抑制过的残差高一个数量级,**不能复用
production cleaned 的色标**,否则整片饱和。"多个 cleaned 结果共用色标"那条规则是为了让两个**去噪**
结果可比,最小处理版不属于那种情况。

### 影响面(改动前已量化)
503 条已审 eCallisto 记录里,保护窗口占比 >70%(改动影响最大的区间)的只有 **62 条(12%)**:
discard 18 · usable 24 · 待重试 20;已审的 16 条 Type II **全部**在此区间。253 条人工时间修正里只有
20 条在此区间,**而且时间修正是看 raw 面板判断的,任何去噪改动都碰不到它们**。
